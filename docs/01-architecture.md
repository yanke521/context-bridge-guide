# 01 · 谁保管聊天，谁负责回复

## 一份总记录，多种使用方式

把用户、会话、渠道和引擎分开：

```text
用户：这个人是谁
会话：正在延续哪段对话
渠道：消息从网页、手机还是消息桥接进来
引擎：这轮用直接 API、CC 续会话，还是无持久会话的 CC
```

同一个人从两个入口进入同一段对话，应得到同一个内部会话标识。换渠道不自动换会话，换引擎也不自动换聊天账本。

身份映射由服务端根据已验证的登录态建立。客户端提交的 `user_id`、昵称或 `conversation_id` 不能直接成为读取其他人记录的通行证。

## 一轮消息怎么走

1. 渠道适配器把输入转成统一事件，保留来源消息 ID。
2. 服务端验证身份，把事件映射到内部会话。
3. 对同一会话的一整个回合排队，去掉重复投递。
4. 先记录用户消息；根据账本、记忆和当前问题组织上下文。
5. 把资料包交给选中的引擎；工具调用也属于这一回合。
6. 保存最终回复、工具结论和原文附件引用，再广播给其他在线端。

统一事件可以长这样，字段值全部为虚构示例：

```python
event = {
    "conversation_id": "demo-conversation",
    "source_event_id": "phone-message-42",
    "channel": "phone",
    "role": "user",
    "text": "我刚才说的检查时间是什么时候？",
    "received_at": "2026-11-14T12:00:00Z",
}
```

## 总记录和“本次给模型看的内容”分开

账本保存原文和事件来源。本次请求可以只带一段摘要和最近原话。压缩的产物应是一份请求视图，不要拿它覆盖原始聊天记录。

同样，在线内存窗口可以只保留近期消息；更早的原文仍归档保存。缩短内存窗口和缩短模型上下文，是两个不同的动作。

原应用把多个入口统一交给主服务写入聊天记录，避免几个进程分别“读文件 → 改列表 → 整份覆盖”互相盖掉消息。更完整的实现还需要把整个模型回合串行化：仅仅锁住写文件的那几毫秒，不能保证两轮并发生成时都读到了对方的回复。

## 不同引擎共享什么

| 状态 | 应由应用保管 | 可以是引擎临时状态 |
|---|---:|---:|
| 聊天原文、来源和次序 | 是 | |
| 摘要、重要约定、长期记忆 | 是 | |
| 实际文件和附件引用 | 是 | |
| CLI session ID、缓存热度 | | 是 |
| 正在执行的一组工具调用 | 执行期间需要登记 | 是，但不能随便丢 |
| 模型隐藏推理 | 不作为可迁移记忆来源 | 是 |

API 和 CC 之间能稳定传递的是“对话含义和明确结果”。隐藏推理、内部运行栈、所有工具原始输出，不会因为按钮切换就自动迁移。

## 从最小系统开始

先实现一个聊天入口、一个权威账本和一个上下文组装器，再加渠道与引擎适配器。增加渠道时，优先复用同一条主处理路径，少复制一套“差不多”的聊天逻辑。
