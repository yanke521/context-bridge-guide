# 07 · 怎样知道它真的接上了

## 用虚构事实做一组小测验

不要用真实隐私聊天做公开复现。准备固定的虚构事件和标准答案：

```text
早期事实：项目代号 LIME-73
明确约定：周五 16:20 检查
后来更新：检查改为周五 17:10，原时间作废
工具结论：测试文件中的标记是 TOOL-91
未完成项：还没决定在哪里碰面
```

测试时问“几点”“地点定了吗”“哪个时间已经作废”，比只问“你还记得吗”更容易判断质量。

## 建议的验证矩阵

| 场景 | 需要检查 |
|---|---|
| 连续 API 聊天 | 当前消息只出现一次，事实不被错误归属 |
| 超过摘要阈值 | 摘要保留约定、更新和未完成状态；原账本不变 |
| 大段代码 / 附件 | 有引用，必要时可回查，不悄悄吞掉整个原文窗口 |
| 检索失败 / 摘要失败 | 错误可见，不把空结果写成“没有这件事” |
| 网页 → 手机 | 两端映射同一会话；新回合读到前端刚写入的事件 |
| API → CC → API | 两条适配路径收到同一份事实与当前状态 |
| 原 CC ↔ 一次性 CC | 消费游标独立；补课不跳过尚未读过的事件 |
| 手机工具结果续接 | ID、归属、次序、超时和重复回传处理正确 |
| 两端同时说话 | 同一会话完整回合排队；不同会话可独立运行 |
| 客户端断线 / 服务重启 | 明确能恢复到哪一步，避免重复副作用 |
| 缓存跨分钟 / 改工具 | 比较实际 usage 和账单，观察失效位置 |
| 模型窗口接近上限 | 预留工具与输出空间，失败不裁账本 |

## 记录事件，不一定记录正文

默认观测信息可以是：

```text
trace_id / conversation_id / source_event_id / turn_id
channel / engine_kind / engine_instance_id / model
history_count / history_estimate / estimate_method
summary_source_range / summary_version / summary_reused
recall_count / injected_size / selected_source_ids
cache_read / cache_create / ordinary_input / output
tool_call_id / delivery_state / error_kind
```

会话 ID 和来源 ID 本身也可能敏感，实际日志可以再使用内部化或散列标识。正文、凭据和完整请求默认不进入公开观测记录。需要本地请求快照时，另外控制保存位置、访问和保留时间，不和分享仓库混在一起。

## 区分几个“频率”

每轮都运行上下文组装，不等于每轮都调用摘要模型。每轮都携带一份摘要，不等于摘要这轮被改写。

分别记录 `context_built`、`summary_reused`、`summary_generated`、`session_rotated` 和 CLI 自己的压缩事件，才能回答“多久压一次”。没有成功事件日志时，应说“无法统计”，不要用阈值倒推出准确次数。

## 小步上线与回退

为新适配器增加独立模式，不覆盖旧会话状态；先用虚构内容验证，再让用户主动选择。调整摘要参数时，保留旧值和变更理由，比较标准问题的答案。

至少留下：代码版本、摘要器版本、模型、端点能力配置、可切回的旧模式，以及每条记忆指向的原始来源。回退代码不会自动撤销已经执行的外部工具动作，这部分要单独查询或补偿。

## 本仓库实际验证到哪里

仓库测试只运行本地教学实现，验证共享历史、摘要缓存键、完整回合窗口、消息去重、失败重试、会话隔离、缓存标记和 CLI 输入边界。它不发请求，不花模型额度，不执行 Claude Code，也不会生成真实缓存命中率。

真实项目中曾验证中转驱动 Claude Code 的读文件和跨轮事实续接。这种小规模通过，不能代替长期聊天的记忆质量测试，也不能证明所有模型、图片和手机工具都兼容。

任何分享时的“通过”都应带上范围：用什么输入、经过哪条路径、检查了哪些结果、还没覆盖什么。
