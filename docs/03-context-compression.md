# 03 · 旧事整理成摘要，近事保留原话

## 我们想保留的结构

```text
往日目录：哪天发生过什么，去哪里找原文
今天早些时候：已滚出原文窗口，但仍需要接上的事
最近原话：保持对话细节和说话语气
重要备忘：约定、待办、位置等需要明确记住的事实
```

目录负责指路，摘要负责接上，最近原话负责细节。重要约定可以单独记成备忘，不必靠扩大原文窗口才能保住。

## “四万”到底是什么

原应用当前的 API 压缩判断使用一把粗略尺子：

```python
estimated = len(json.dumps(role_and_content, ensure_ascii=False)) // 2
trigger = 40_000
recent_tail_budget = 15_000
```

这里“四万”不是官方 tokenizer 的四万 token。它主要计算历史消息的 `role`、`content` 及序列化格式开销；正文内的代码也算。旧摘要先单独处理，部分大作品在请求视图中缩成引用。没有把系统设定、工具定义、独立思考字段和另外注入的资料全部算进去。

因此，触发压缩时，实际请求可能已经远超过四万真实输入 token。中文、英文、代码和图片的比例也不同。这个数字是该应用的历史参数，不能直接套到别人的模型窗口。

完整预算应覆盖工具、系统、摘要、历史、召回、最新输入，以及输出和单轮工具结果的余量。能使用服务端 token counting 时，应以它校准估算；使用计数接口本身也需要验证网关是否支持。[Token counting 官方文档](https://platform.claude.com/docs/en/build-with-claude/token-counting)

## 每轮检查，不等于每轮重写摘要

每次生成前都准备请求视图。超过阈值后，后续请求也可以持续使用摘要与原文窗口。

原应用为摘要设了复用缓存，并按滚出窗口的消息数量分桶更新，例如每跨过约二十五条才重算一段。这个策略减少摘要调用，但并非“每聊二十五条就压缩”，也不是准确的时间频率统计。

公开示例使用更容易检查的做法：根据**被摘要原文的内容、事件 ID 和摘要器版本**生成缓存键。相同输入复用摘要；历史被修改、会话不同或摘要器升级时重新计算。不能只拿“消息数一样”判定摘要相同。

## 摘要应该记什么

可以按话题分块，再使用不同侧重：

- 任务与技术：决定、被否定的方案、文件名、完成情况、下一步。
- 日常事实：准确的时间、地点、数量、承诺和状态变化。
- 关系与情绪：由什么引起、双方明确表达了什么、是否解决。

共同要求是：保留说话人，保留未完成事项，不编造因果或承诺。用“用户说……”“助手答应……”这样的明确归属，避免把历史摘要里的“我”错当成最新用户正在说话。

不要把每次摘要都当作新的原始事实。保留摘要覆盖到哪些事件、使用哪个版本的提示、何时生成，以便回查。

## 别切断工具交换

模型刚发出 `tool_use`、结果还没回来时，不应换会话或压掉半个工具交换。保留完整的调用与结果，等当前任务回合完成，再整理跨轮上下文。

示例以完整 `turn_id` 分组移动原文窗口。一组太大时会保留整组，并标记超出尾部预算；调用方仍需做完整请求容量检查。不能为了凑一个漂亮的数字，把参数、结果或关键结论裁掉一半。

## 压缩失败怎么处理

保留原始账本，把失败记录下来；可以使用已知覆盖范围的旧摘要，或者返回需要缩小请求的错误。不要把“摘要调用失败”当成“这段没有重要内容”，也不要悄悄丢掉最老一半记录后宣称记忆完整。

原应用仍有旧摘要逻辑作为异常回退，这是应观测的风险点。教程示例选择显式抛错，让失败可见；它没有复制静默降级行为。

对应例子：[ContextBuilder](../examples/context_core.py)。示例摘要器是教学替身；接模型摘要器后，要另外验证事实保留和长期连续性。
